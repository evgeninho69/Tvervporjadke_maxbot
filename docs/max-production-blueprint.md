# MAX Integration: Production Blueprint

## 1) Что нужно предоставить, чтобы получить рабочий доступ и начать разработку

### 1.1 Доступы и регистрация

1. Подтверждение, что бот зарегистрирован в MAX и есть production token.
2. Роль/доступ в кабинете MAX для управления bot profile и webhook subscriptions.
3. Подтверждение юридического контура (для partner доступа, если требуется по правилам MAX).

### 1.2 Секреты и параметры

1. `MAX_BOT_TOKEN` (production и, отдельно, stage).
2. `MAX_API_BASE_URL` (обычно `https://platform-api.max.ru`).
3. `MAX_WEBHOOK_PUBLIC_URL` (публичный HTTPS endpoint).
4. Опционально: allowlist исходящих IP (если политика периметра требует).

### 1.3 Инфраструктура

1. Публичный домен под webhook (например `max-bot.tver.example.ru`).
2. TLS-сертификат (valid chain, без self-signed для production).
3. Очередь сообщений (NATS/Rabbit/Redis Streams/Kafka) для буферизации событий.
4. Хранилище для outbox и idempotency (Postgres).
5. Наблюдаемость: метрики, централизованные логи, алертинг.

### 1.4 Интеграции проекта

1. Доступ к backend ActiveTver API (service account / mTLS / internal token).
2. SMTP/SMS/push шлюзы (если будут мультиканальные уведомления).
3. Карты/геокодер (если нужны адресные подсказки, reverse geocoding).

### 1.5 Нефункциональные требования

1. SLA по времени обработки заявки и по доставке уведомлений.
2. Политика хранения персональных данных и сроков ретенции.
3. Правила модерации контента/медиа.

## 2) Что обязательно учитываем из MAX документации

1. В production используем webhook, long polling оставляем только для dev.
2. Webhook должен быть на HTTPS.
3. Токен передается в `Authorization` header.
4. API лимит: до 30 rps, значит нужно проектировать rate limiting и очереди.

## 2.1 Что подтверждено в рабочей стадии

1. Входящий текст приходит в `message.body.text`.
2. Идентификатор чата приходит в `message.recipient.chat_id`.
3. Для отправки сообщения корректен формат:
   - `POST /messages?chat_id=<id>`
   - body `{ \"text\": \"...\" }`
4. При конфликте webhook и polling входящие могут не приходить в polling до удаления подписки webhook.
5. Удаление подписки webhook практично делать через:
   - `DELETE /subscriptions?url=<encoded_url>`

## 3) Production-версия решения (не MVP)

## 3.1 Архитектура

1. `at-max-bot-gateway`:
   - принимает webhook
   - валидирует заголовки/формат
   - пишет event в очередь
2. `at-max-bot-worker`:
   - обрабатывает команды и диалоги
   - вызывает ActiveTver backend API
   - пишет исходящие уведомления в outbox
3. `at-max-notifier`:
   - доставляет сообщения в MAX API
   - retry/backoff/jitter
   - DLQ при исчерпании попыток
4. `at-max-miniapp`:
   - сложные формы и workflows
   - личный кабинет заявителя
5. `ops/observability`:
   - dashboards, alerts, audit trails

## 3.2 Основные данные (таблицы)

1. `messenger_links`:
   - `uid`, `messenger`, `chat_id`, `verified_at`, `status`
2. `incoming_updates`:
   - `update_id`, `received_at`, `processed_at`, `result`, `error`
3. `conversation_state`:
   - `chat_id`, `flow`, `step`, `payload`, `updated_at`
4. `notification_outbox`:
   - `id`, `channel`, `chat_id`, `template`, `payload`, `attempt`, `next_retry_at`, `status`
5. `notification_delivery_log`:
   - итог доставки/ошибки для аналитики и поддержки

## 3.3 Безопасность и надежность

1. Secrets только через vault/secret manager.
2. Логи без токенов и без сырого PII.
3. Idempotency на входящих апдейтах и исходящих сообщениях.
4. Dead-letter + ручной replay инструмент.
5. Контроль версий контрактов между сервисами (API schema).

## 3.4 Операционная модель

1. On-call процесс и runbook для инцидентов.
2. Классификация инцидентов (P1/P2/P3) и регламенты эскалации.
3. Release policy:
   - canary deploy
   - feature flags
   - быстрый rollback

## 4) Избыточный каталог функций (для последующего выбора)

## 4.1 Функции для граждан

1. Пошаговое создание заявки в чате:
   - категория, адрес, геопозиция, фото/видео, описание.
2. Создание заявки через mini app с проверкой качества данных:
   - подсветка незаполненных полей
   - гео-валидация
   - предпросмотр перед отправкой
3. Автопоиск похожих заявок рядом:
   - предотвращение дублей
   - предложение "присоединиться к существующей проблеме"
4. Статус-трекер:
   - таймер SLA
   - журнал изменений
   - ответственный орган
5. Двусторонний диалог по заявке:
   - уточнения от оператора
   - вложения от заявителя
6. Подписки:
   - на район
   - на категории проблем
   - на экстренные уведомления
7. Новости и объявления:
   - по району
   - по персональным интересам
8. Календарь коммунальных работ в районе.
9. Карта проблем/решений с фильтрами и историей.
10. Голосование по локальным инициативам.
11. Геймификация:
   - рейтинг активных жителей
   - бейджи
   - квартальные челленджи
12. Социальные сценарии:
   - "соседские чаты по дому"
   - "организовать субботник"
13. Шаблоны быстрых обращений:
   - яма
   - неработающее освещение
   - мусор
   - вандализм
14. Доступность:
   - крупный текст
   - голосовые подсказки
   - упрощенный режим
15. Мультиязычность и режим для иностранных студентов/гостей.

## 4.2 Функции для администрации

1. Единый омниканальный inbox:
   - MAX
   - web
   - мобильное приложение
2. Очереди обработки по SLA и приоритетам.
3. Автораспределение заявок по ведомствам.
4. Автоклассификация заявки (NLP + CV по фото).
5. Антифрод/антиспам скоринг.
6. Массовые операции:
   - batch-change статусов
   - bulk-notifications
7. Workflow-конструктор регламентов:
   - разные процессы для разных категорий
8. Контроль исполнителей:
   - срок реакции
   - срок закрытия
   - возвраты на доработку
9. Конструктор официальных ответов (шаблоны + ИИ-черновик).
10. Дашборды:
   - по районам
   - по категориям
   - по подрядчикам
11. Прогнозная аналитика:
   - где вырастет поток обращений
   - где вероятны повторные инциденты
12. Гео-аналитика:
   - heatmap
   - кластеры проблем
13. Инцидентный центр:
   - массовые аварии
   - штормы/снегопады
14. Экспорт в отчеты:
   - CSV/XLSX/PDF
   - регулярные отчеты руководству
15. Аудит и комплаенс:
   - лог действий операторов
   - неизменяемый журнал критичных операций

## 4.3 Интеграционные функции

1. Интеграция с 112 и городскими диспетчерскими.
2. Интеграция с ГИС ЖКХ / муниципальными ГИС.
3. Интеграция с подрядчиками и ticketing-системами.
4. Интеграция с платежами/штрафами (если нужен сценарий оплат).
5. Интеграция с транспортными API (обходы маршрутов, перекрытия).

## 4.4 AI-функции (расширенный контур)

1. AI-ассистент гражданина:
   - "как правильно оформить заявку"
   - "что делать в этой ситуации"
2. AI-ассистент оператора:
   - краткое резюме заявки
   - recommended next action
3. Семантическое дедуплирование обращений.
4. OCR из фото/документов.
5. Автоматическое извлечение адреса из текста.
6. Quality score заявки до отправки.
7. Explainable ML для приоритезации инцидентов.

## 4.5 Надежность/безопасность/эксплуатация

1. Multi-AZ развертывание.
2. RPO/RTO цели и регулярные DR-тесты.
3. Data retention policy и auto-purge.
4. Канареечные релизы и progressive rollout.
5. Реестр feature flags.
6. Автоматические smoke/regression проверки после деплоя.
7. Playbooks для частых аварийных сценариев.

## 5) Рекомендуемый порядок внедрения (production wave)

1. Wave 1:
   - webhook + account linking + create claim + status updates + outbox.
2. Wave 2:
   - mini app, подписки, аналитика операторов, SLA/эскалации.
3. Wave 3:
   - AI/прогнозирование, внешние интеграции, incident center.



Как это работает вместе:
Пользователь находит бота в поиске.

Бот приветствует его и дает кнопку "Открыть Тверь в порядке".

Внутри бота открывается Mini App (дизайн которого мы сделали ранее).

После того как пользователь отправил фото и геопозицию через Mini App, приложение закрывается, и бот пишет: "Принято! Номер вашей заявки 1234".

Когда чиновник в Админке нажимает кнопку "Выполнено", бот мгновенно присылает пользователю уведомление с результатом.

Это создает замкнутый цикл: Бот (Уведомления) <—> Mini App (Ввод данных) <—> Админка (Управление)
